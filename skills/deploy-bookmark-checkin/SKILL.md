# Deploy bookmark check-in

Use the repository root that contains this skill. Keep every user-specific value in ignored local files.

## Workflow

1. Run `scripts/Test-Environment.ps1` without changing the machine.
2. Classify findings as blocking, optional, or ready. Explain each missing capability and its effect. Ask the user to choose whether to install, skip, or use the documented fallback before changing the environment.
3. Read [questionnaire.md](references/questionnaire.md). Before any other setup preference, ask whether to use Chrome or Edge, which browser profile, which parent/container bookmark folders, and which child folders contain the targets. Use candidates from preflight; never assume names from defaults, examples, or another user. Ask only unanswered questions, at most three at a time.
4. Re-run `scripts/Test-Environment.ps1` with `-Browser`, `-ContainerFolderNames`, and `-TargetFolderNames`. Resolve an empty or ambiguous match before continuing.
5. Copy `setup/answers.example.json` to ignored `setup/answers.json` and record the confirmed non-secret answers. Run `scripts/Initialize-Checkin.ps1`.
6. Run the bookmark dry run. Show every matched source, deduplicated site count, and any ambiguous profile selection before browsing sites.
7. Initialize the isolated browser profile. Keep the browser visible only for the initial user-approved login pass; scheduled runs must use the configured off-screen mode.
8. Run one complete check-in without notification. For every unresolved site, first retry and inspect stable page evidence. Use built-in public rules, then generic discovery, then a local adapter. Write local rules only to ignored config files.
   If the user confirms a site is unreachable today after inspecting its manual page, close and save the project browser, then run `scripts/Set-TodayAbandonment.ps1 -Origins <origin> -Reason network_unavailable`. If other pages in a controlled native session still need work, use `-PreserveSession` to record only the selected current-session targets without closing the browser. The observer skips those targets and closes only when every remaining target has bound completion. This records today's skip, retains the failure history, and removes that target from the manual queue. It expires the next day. Never infer this user confirmation from a single automatic timeout or classify the site as permanently closed.
9. Require authoritative success evidence. A click, redirect, empty error, or window title is insufficient.
   Before asking the user to operate a manual window, run `scripts/Get-ManualHandoffStatus.ps1`. Ask only when `mayAskUser` is true, combine its current targets into one request, and retain its `requestId`. Do not send another request while that request is pending. Before acting on a reply, re-run with `-ExpectedRequestId <id>`; an expired request must not reopen or resubmit a completed target. Re-read the current queue and clearly retire obsolete requests when work completes. This status confirms a matching visible project window, not the presence of a particular page control; inspect that page before describing it. If the window is unavailable, restore the project window before asking. A failure or unresolved response is never permission to close a window before a stable completion signal or explicit abandonment.
   For a tracked native session with `controlledCheckin: true`, use `scripts/Resume-ManualCheckin.ps1` after login or verification to continue ordinary check-in controls on the retained page. `Close-ManualLogin.ps1` runs this continuation before closing and retains unresolved pages. Use `-SaveOnly` only for an explicit save-and-close request, or `-Abandon` for an explicit abandonment; neither is success evidence. Login-only sessions keep remote debugging disabled.
   Controlled windows also run a session-bound observer every five seconds. It follows delayed verification readiness, submits ordinary ready controls once, and closes only after bound completion for all targets. It never reloads a retained form or starts another verification-click round. While a request is pending, use `Get-ManualHandoffStatus.ps1 -ExpectedRequestId <id> -WaitSeconds 30` to observe changes; an active session means the overall task is still in progress. If it finishes before the user replies, retire the request and report `requestState`, `resolvedTargets`, and the recorded closure reason. Do not ask the user to operate a completed or closed page.
   Eligible ordinary continuations run before a long-lived same-page session. Completed or explicitly abandoned sessions dispatch the remaining queue once; this dispatch does not install scheduling, send notifications, or restart the full daily run. Same-page HTTP rejection diagnostics must remain distinct from login, wrong-page and verification waits. An abandonment close signal must retain its `abandoned` reason in session history.
   Visible Agent Router OAuth records an identity-bound login checkpoint before emitting its result. Its session observer may finish saving that exact window if the opener is interrupted; the reward request is persisted before closure and remains pending while another manual session owns the run lock. This login checkpoint never counts as reward evidence.
10. Read [acceptance.md](references/acceptance.md), run all acceptance checks, then install scheduling. Use the Windows task when permitted; otherwise use the user-level hidden scheduler only if the user accepted the fallback.
11. Run `scripts/Scan-PublicSafety.ps1`. Report installed mode, schedule, site totals, unresolved sites, notification behavior, and recovery instructions.

Read [compatibility.md](references/compatibility.md) when preflight is not fully ready. Read [site-adapters.md](references/site-adapters.md) when adding or reviewing site rules.
