# Site adapters

Keep public rules in `config/site-rules.public.json` and private rules in ignored `config/config.local.json`.

An ignored `linuxDoLoginRecovery.socialProvider` preference may select `GitHub`, `Google`, `Discord`, or `Apple` on the official LinuxDO login page. Retained native sessions wait for visible login verification to clear, then click the configured social control once per tracked session before continuing consent and target-session verification. They never infer daily rewards from that login checkpoint. Login, missing-page, ambiguous-page and pending-verification diagnostics contain only fixed categories.

Controlled ordinary continuations serialize on their session marker before acquiring the shared run lock. A busy result is retryable and keeps the window open; callers re-read the session identity after waiting. Partial today-only abandonment may coexist with a dedicated account window only when the selected ordinary targets and browser profiles are independent.

A rule may define related candidate URLs, logical duplicate groups, visit-after-time behavior, native WAF preflight URLs, OAuth redirects, and confirmed no-feature origins. Navigation must remain within the bookmark origin or explicitly allowed related origins.

For a native CF-before-submit form, `nativeChallengePreflight` may use `samePageCheckin: true` with one matching native `samePageManualCheckinRules` entry and one sequential step at the exact same URL. This shares the retained-page runner between automatic and manual phases: it waits for the configured response before submitting the exact action once. Keep navigation links out of the action texts and tags. Missing verification or ambiguous submission goes to manual continuation without generic fallback or a second submission.

A reviewed native daily form may locally opt into `allowSubmitWithoutChallenge: true` when the site sometimes renders no verification at all. Require the same fully loaded authenticated document for two seconds, one enabled action in a same-origin POST form at the exact configured path, and no verification host (including hidden hosts), response field, captcha script, password form, or extra non-hidden input. An empty token or loading widget still waits for verification. Current unresolved submissions remain protected; this option never releases an intent.

An ignored `navigationObservationRules` entry may list exact `paths` and a `waitMs` budget up to 40000 for a known slow page. After a navigation timeout at that exact destination, inspect only the fully loaded current document and discard observations if the document changes. Stop on a stable completion, login, challenge or deferred signal; otherwise report an unconfirmed load. Never reload, navigate or submit from this observation fallback.

For a site that requires retaining its login and verification document, an ignored `samePageManualCheckinRules` entry may opt into `browserMode: "native"` with one matching sequential step. The controlled native session reuses the logged-in tab without navigating or reloading it. After an uncertain submission, observers only inspect completion; they do not repeat the button click or abort the site's delayed verification replay. A local `nativeClickChallenge: true` allows one bounded verification attempt on the initial continuation, never repeated observer rounds. Native control uses a loopback debugging port, so a successful manual comparison without debugging does not guarantee automated verification will pass.

Sequential clicks record fixed phases for control discovery, trial click, control recheck, intent reservation and actual click invocation. A known failure before actual invocation may retry once only while no durable intent or action request exists; zero matched requests alone never permits a retry. Later same-page observations retain the first failure category separately from the current state. A visible password form on another same-origin page is classified as waiting for login, rather than waiting for the check-in page.

Scoped same-page supplements use `writeScopedCheckinResult` from `src/logger.mjs` for failed observations as well as successful completion. Keep the sanitized click phases and request/rejection counters in both the report and submission history across restarts. These counters are diagnostic only; they never replace the bound frozen rejection receipt and fresh authoritative unsigned status required by the existing recovery mechanism. Closed-root challenge inspection reads visible loading, failure, expiry and success panels even without a checkbox, and reacquires a replaced iframe before starting a new stability interval within the same bounded attempt.

A one-step ordinary check-in may specify `entryNavigation` with an exact `homePath`, `linkText`, and `loginText`. The runner follows only the unique visible link whose destination matches the configured step URL, without reserving a submission for navigation. A unique login control without the entry link on that homepage routes to manual login. Use exact action text and tags for submission and an exact completed control for success; `matchByText: true` requires one matching visible control when the selector also matches unrelated controls.

A daily sequential step may use a locally reviewed `dailyUnsignedControl` with an exact selector and anchored text pattern when the site's rendering explicitly distinguishes today's unsigned state from completion and makeup actions. It supplies negative readiness only on the loaded, idle, unchallenged page; it never confirms completion. Native same-page continuation rechecks this state immediately before reserving a new day's intent. Native action continuation may use its configured authoritative status reader for the same purpose. Both retain historical uncertain entries and refuse a new action while any current-cycle intent remains unresolved. A generic enabled button alone cannot release a historical lock.

Native checkpoints omit null action placeholders. Readers also normalize legacy `actionResults: [null]` to an empty array; declared sequential steps still require their own matching completion evidence.

After a login-only native window is normally closed by the agent, `Close-ManualLogin.ps1` starts one quiet, targeted `Run-Checkin.ps1` attempt for that session's recorded `login_required` sites, or `needs_attention` sites explicitly marked `loginRecoveryRequired` after `login_recovery_requires_manual`. The runner revalidates the current-day pending scope and matching session identity before browsing. Other attention states, `-SaveOnly`, external closure and abandonment do not start this attempt. Login or closure alone never confirms check-in.

An existing `visitCheckinRules` entry can also use controlled native continuation. It inspects the retained page, honors the configured opening time, verifies the saved-login session, and binds the result to the current target and cycle before reconciling the daily report and manual queue. An explicit authenticated-visit assumption remains `user_rule` evidence with `authoritative: false`. This path never clicks a submission control or replaces sequential or account-specific reward rules.

An exact sequential rejection rule may declare `verificationRequired: true` only after confirming the site's verification handshake. Combined with `siteReplaysAfterChallenge: true`, a matched response means waiting for the site's own replay, not releasing the submission intent. Generic HTTP 422 responses remain rejections. Diagnostics store only counters, relative times and public numeric verification codes; never persist response bodies, console text or verification tokens.

A native one-step daily rule may explicitly opt into `retryRejectedVerification: true`. One retry per cycle is allowed only for the live intent after every observed action request matches an exact verification rejection, no response remains pending, the widget and response disappear, and the reviewed daily unsigned control stays ready for two seconds in the same document. The runner freezes the exact endpoint, rechecks readiness, and atomically retains the rejection and reserves the retry. Active widgets, unknown responses, network failures, old unobserved intents and generic enabled buttons remain protected. Observer passes do not start another verification-click round. Persist the actual verification-click outcome alongside request counters.

Controlled manual progress carries its check-in cycle. A previous cycle's attempt flags cannot force today's session into read-only mode; the durable submission journal still decides whether a new cycle may submit. Historical-only blocks remain until fresh reviewed daily unsigned evidence is available, and do not set `currentCycleSubmissionAttempted`. Initial verification probes may reacquire a delayed or loading iframe within one bounded attempt, ending after one actual click or an explicit failure. Observer passes do not click verification controls. Validated `not_available` results also complete session closure and advance the remaining queue, without being reported as signed or permanently disabling the site.

An ignored `newApiFeatureStatusOrigins` list can opt a native target into a read-only `/api/status` feature check before submission guards or challenge actions. Only successful same-origin JSON with `success: true` and strict `data.checkin_enabled: false` confirms `not_available`. Failed reads, missing flags and string values never disable a feature. Preserve this evidence through preflight and recheck in each new cycle.

Image captcha submission uses natural image pixels and the generic alphanumeric recognizer where the reviewed site requires it. OpenCD uses its dedicated font recognizer. Its adapter accepts the exact authenticated homepage completion control, including the unique check-in history link that replaces the unsigned control after a successful refresh; generic history text on other sites is insufficient. Opening its captcha iframe is navigation within the page, so reserve submission intent only before the actual captcha submit. One retry per cycle requires a live, explicitly rejected captcha response, exactly one request and response, a frozen action endpoint, and fresh bound unsigned page evidence. Preserve both attempts in the journal and retain the retry budget across restarts. Unknown responses, HTTP/network failures and historical uncertain intents never release protection. Response diagnostics contain counts, confidence and HTTP status only; recognized text and raw responses remain in memory. Stable page completion is still required after submission.

OpenCD first matches six natural-pixel glyphs against the public libgd Giant font. Require both a high similarity and a clear lead over the next candidate; ambiguous O/Q shapes remain rejected. When at least four glyphs establish this font but another glyph is uncertain, return no answer instead of letting general OCR override the rejection. Unrecognized fonts retain the existing OCR fallback and confidence floor. Wait within a bounded interval for the authenticated homepage to load and for its clicked entry to attach the exact unique same-origin iframe; never click the entry again merely because the iframe is delayed. Keep private calibration images out of public fixtures and retain the font attribution in `THIRD_PARTY_NOTICES.md`.

A client-blocked native daily form must not be mistaken for an authenticated home page with a missing check-in link. Bind actual browser error documents using matching CDP navigation history and target metadata. With no current-cycle pending submission, recover a uniquely identified daily form once to its configured home and follow its visible entry; a native same-page target may restore only its exact configured entry. Persist the attempted recovery across observer passes. Never refresh a normal verification form, navigate to a configured terminal path, or bypass certificate/security warnings. Native form request guards record fixed block counters and remove their own routes before disconnecting. These counters distinguish a project-side abort from an unexplained browser block; they do not establish the historical cause of an earlier error.

When a site explicitly replaces web check-in with WeChat mini-program check-in, an ignored `manualCheckinRouteRules` entry may set `kind: "wechat_mini_program"`, a same-origin `pagePath`, and bounded exact `controlTexts`. This produces pending manual work without clicking the entry, reading QR data, assuming completion, or permanently disabling check-in. A user-requested skip remains limited to today.

An ignored `piggoCalendarRules` entry can enable the reviewed calendar reader. It opens and closes a separate passive project tab, observes the page's own GET responses for `/v1/web/me` and `/v1/web/calendar`, and requires fresh server dates, the selected current day and a valid account fingerprint. It never copies authentication values or reloads the retained check-in page. HTTP 423 `idle_locked` is an unlock requirement, distinct from a missing login. The passive tab blocks same-origin writes only; it does not block verification assets or WebSockets in the retained page.

`unsignedSubmissionRecoveryRules` is private opt-in and currently accepts only `reader: "piggo_calendar"` with the exact sequential `actionType`. One recovery per cycle requires fresh API unsigned evidence, the same hashed account and browser profile as the original intent, a newer retained document, and no active verification or late action request. The journal atomically consumes the evidence and reserves a replacement intent. Original unknown outcomes remain in audit history. Legacy intents without account binding, generic buttons, stale receipts and other sites cannot use this path.

NexusPHP image verification requires the visible input, image and submit button in one authenticated POST form. The generic recognizer retains a confidence floor of 60; OpenCD keeps its separate recognizer and floor of 55. Hash the hidden challenge value with natural image pixels in memory, recheck after OCR, and never resubmit the same challenge. Only one exact captcha refusal can admit one fresh-question retry; keep its endpoint frozen and monitored during recognition. An ambiguous response never reloads the attendance page. Reviewed passive daily status takes precedence over generic page text after submission.

`npm run unknown:summary` reads stored run reports without browsing or changing the submission journal. It groups anonymous targets by date and distinguishes request-observed, click-dispatched, verification-wait, pre-dispatch-failure and missing-observation rows. Repeated rows across runs remain separate; these totals are report-row counts, not submission counts.

OpenCD homepage entry discovery also accepts one exact visible check-in link with a same-origin plugin destination or an inert in-page link, after confirming the authenticated homepage and absence of login or verification controls. Require its exact same-origin captcha iframe before submission. Completion uses the shared page-text classifier as well as the reviewed controls, with two consecutive read-only observations and at most one homepage reload after explicit server success. Unknown outcomes never reload or resubmit.

`Run-Checkin.ps1 -Origins` may combine pending manual verification with other requested targets. It passes their exact intersection separately using `--manual-verification-scope` (`none` for an empty intersection). The guard requires the current resume report and validates that intersection; only those pending targets are consumed, with other pending records retained. Verification targets are ordered before the remaining selected targets in the same locked run.

Native continuation diagnostics use fixed categories and phases for connection, target selection, page stability, helper timeout, helper exit and invalid output. Persist only those fields and a bounded numeric exit code. Never store raw helper output or error messages. A failed helper preserves any current-cycle submission intent and cannot authorize a new click.

Before adding a public rule:

1. Remove usernames, email addresses, balances, account IDs, invite codes, tokens, query secrets, screenshots, and history excerpts.
2. Prove the rule from stable public structure or a successful local page signal.
3. Add a detector or routing test.
4. Do not cache an answer until the site confirms it was correct.
5. Do not mark a feature unavailable solely because no button was found; prefer an authoritative API or settings flag.
